# StockLog 문제 해결 기록 (포트폴리오 / 노션용)

> 노션에 그대로 붙여넣을 수 있는 마크다운입니다.
> 각 항목은 **문제 → 원인 → 해결 → 결과** 순서입니다.
> `📏 측정 필요`로 표시한 곳은 아직 숫자로 검증하지 않은 부분이니, 실제 수치를 넣으면 설득력이 올라갑니다.
> `상태`는 실제로 반영한 것(✅ 해결)과 원인만 분석한 것(🔍 분석 완료)을 구분했습니다.

## 1. 매매 신호 판정 로직이 세 곳에 흩어져 있던 문제 — ✅ 해결

**문제**
- 진입 신호 판정이 `EntrySignalAnalyzer`, `SignalRule` 계열(`MomentumRule`, `RsiSignalRule`, `TrendAndMaRule`), `TradingSignalAnalyzer`에 나뉘어 있었다.
- 같은 종목인데 화면, 포트폴리오 검증, AI 코멘트가 서로 다른 기준을 쓸 수 있었다.

**원인**
- 새 엔진(`TradingSignalAnalyzer`)을 만들면서 기존 규칙을 옮기지 않고 병행 운영했다.
- `SignalRule` 인터페이스가 정말 필요한지 따져 보니, 규칙들이 같은 입력(`MarketContext`)과 같은 출력(점수 가중치)만 쓰고 있어 분리할 이유가 없었다.

**해결**
- 규칙 로직(`MACD`, `RSI` 극단/다이버전스, 추세·이동평균)을 `TradingSignalAnalyzer` 내부 메서드(`momentumSignals`, `rsiSignals`, `trendAndMaSignals`)로 이동하고 `SignalRule` 주입을 제거했다.
- 가중치를 `SignalWeight` enum으로 모아 매직 넘버를 없앴다.
- 삭제 대상을 정리하고, 이후 `EntrySignalAnalyzer` 삭제로 깨진 연결부(`GeminiAiProvider`, `StockFacadeAnalyzer`, `StockAnalysisService`, `PortfolioApiController`, `StockController`)를 연쇄 수정했다.

**결과**
- 신호 판정이 단일 엔진으로 모여 화면, 매수 검증, AI 프롬프트가 같은 결과를 본다.
- 한 곳만 고치면 되는 구조가 됐다. 📏 측정 필요: 삭제/통합한 클래스 수와 코드 줄 수.

**배운 점**
- 엔진을 교체할 때는 "새 코드 작성"보다 "옛 코드를 쓰던 호출부를 전부 찾아 바꾸는 일"이 더 크다. 삭제 전에 참조 검색을 먼저 해야 한다.

## 2. AI API 키가 로그에 노출될 수 있던 문제 — ✅ 해결

**문제**
- Gemini 호출 실패 시 예외 로그에 API 키가 그대로 남을 수 있었다.

**원인**
- 키를 URL 쿼리(`?key=...`)에 넣고 있었고, `RestTemplate`의 예외 메시지에는 요청 URL이 포함된다.

**해결**
- 키를 `x-goog-api-key` 헤더로 옮기고 URL에서는 제거했다.
- 로그는 예외 클래스명과 메시지만 남긴다.
- 응답에 본문이 없을 때(안전 필터 차단, 토큰 초과)는 `finishReason`/`blockReason`을 로그로 남겨, 이전에 NPE로 뭉뚱그려지던 원인을 구분할 수 있게 했다.

**결과**
- 로그/예외 메시지에 인증 정보가 포함되지 않는다.

**배운 점**
- 외부 API 키는 URL이 아니라 헤더로 보내야 한다. 예외 메시지와 로그에 어떤 정보가 따라가는지까지 확인해야 한다.

## 3. AI 코멘트가 분석 엔진 판정과 모순되던 문제 — ✅ 해결

**문제**
- 엔진이 "눌림 구간 대기"로 판정했는데 AI가 즉시 매수를 권하는 식의 문장이 나올 수 있었다.
- 엔진이 계산하지 못한 가격(N/A)을 AI가 임의로 만들어낼 위험이 있었다.

**원인**
- 프롬프트에 엔진의 최종 판정(`Verdict`)이 없었고, 가격이 없을 때의 처리 지침도 없었다.

**해결**
- `Verdict`를 사람이 읽는 문구(`진입 실행 가능`, `눌림 구간 대기`, `추격 위험`, `손익비 부족`, `진입 계획 없음` 등)로 바꿔 프롬프트에 넣었다.
- 지침으로 "엔진 판정과 모순되는 행동 금지", "N/A 가격은 임의 생성 금지, 조건으로만 서술"을 추가했다.
- 차트 데이터가 부족하면 `INSUFFICIENT_DATA`를 "판정 불가"로 안내한다.
- `String.format` 플레이스홀더 개수와 인자 개수가 어긋나지 않도록 점검했다.

**결과**
- AI 코멘트가 엔진 결과를 근거로 한 행동 지침을 낸다. 📏 측정 필요: 판정별 샘플 몇 건으로 모순 여부 확인.

**배운 점**
- LLM에게는 결론(판정)을 데이터로 주고 해석만 맡겨야 한다. 계산은 코드가, 서술은 AI가 하도록 역할을 나눈다.

## 4. 엔진 교체 중 화면이 깨지던 문제 — ✅ 해결

**문제**
- `StockAnalysisResult`에서 `signals` 필드를 제거하자 `analysis.html`이 `${analysis.signals}`를 읽다가 오류가 났다.
- 컨트롤러에서 `TradingSignalAnalyzer`를 한 번 더 호출해 같은 분석을 두 번 계산하고 있었다.

**원인**
- 모델 속성을 바꾸면서 그 속성을 쓰는 템플릿과 컨트롤러를 함께 추적하지 못했다.

**해결**
- 컨트롤러가 가치·수급·차트 분석기의 `getSignals()`를 합쳐 `signals` 모델 속성과 `signalDescMap`을 만들고, 템플릿은 `${signals}`를 읽도록 수정했다.
- 분석 결과는 `analysisResult.getTradingSignalResult()`를 재사용해 중복 호출을 없앴다.

**결과**
- 화면 크래시가 사라졌고 분석 계산이 요청당 한 번으로 줄었다. 📏 측정 필요: 요청당 응답 시간 비교.

**배운 점**
- 서버 모델과 템플릿은 하나의 계약이다. 모델 필드를 바꾸면 템플릿의 `th:` 표현식까지 검색해서 같이 수정한다.

## 5. 분석 결과를 화면에서 충분히 쓰지 못하던 문제 — ✅ 해결

**문제**
- 엔진이 `verdict`(진입 실행 가능 / 눌림 대기 / 추격 위험 등)와 진입 구간 하단(`zoneLow`), 반등 확인(`triggerConfirmed`)을 계산하는데 화면에는 "진입 구간 상단"만 나왔다.
- 사용자는 지금 사도 되는지, 기다려야 하는지 알 수 없었다.

**원인**
- 템플릿이 사용하는 모델 값을 정리해 보니(약 40개 필드), 엔진이 만든 값 중 판정과 구간 관련 값이 화면에서 쓰이지 않고 있었다.

**해결**
- 판정 배지를 타점 카드 맨 위에 추가했다 (실행 가능 / 대기 / 추격 위험 등 6가지, 알 수 없는 값은 표시하지 않음).
- 현재가와 진입 구간을 한 줄로 보여 주고 "구간보다 N% 위/안/아래"와 반등 확인 여부를 배지로 표시했다.

**결과**
- 한눈에 지금 상태를 읽을 수 있다. 서버 `Verdict`와 템플릿 위치 판정이 경계값에서 다를 수 있어, 서버에서 위치를 내려받는 방식으로 후속 개선이 필요하다.

**배운 점**
- 계산을 잘해도 보여 주지 않으면 사용자에게는 없는 기능이다. "화면이 쓰는 값"과 "엔진이 내는 값"을 주기적으로 대조한다.

## 6. 페이지 이동 시 `NoResourceFoundException: /static` — ✅ 해결

**문제**
- 에러 페이지의 "홈으로" 링크와 사이드바 로고가 `/static`으로 이동하면서 `No static resource static` 예외가 발생했다.

**원인**
- 기존 템플릿의 `@{/static}`이 라우트가 아니라 정적 리소스 경로로 해석되고 있었다. 리팩토링 중 기존 링크를 확인 없이 그대로 가져온 것이 원인이었다.

**해결**
- 홈 링크를 `@{/}`로 바꾸고 `/templates/...` 접두사를 제거했다.

**결과**
- 해당 예외가 사라질 것으로 보인다. ⚠ 실제 컨트롤러 매핑(`/auth/login`, `/market` 등)과 일치하는지는 서버에서 확인이 필요하다.

**배운 점**
- 코드를 옮길 때 "그대로 둔다"는 것이 곧 "검증했다"는 뜻은 아니다. 라우트 문자열은 컨트롤러 매핑과 대조한다.

## 7. 시장 국면 confidence가 항상 한 자리 — 🔍 분석 완료 (코드 반영 전)

**문제**
- 화면의 "분석 신뢰도"가 계속 한 자리 수로 나와 항상 회색(낮음)으로 보였다.

**원인**
- `confidence = round(abs(weightedScore))`로, 가중 평균의 절댓값을 신뢰도로 쓰고 있었다. 지표가 서로 엇갈리면 점수가 상쇄되어 0에 가까워진다. 화면 툴팁은 "지표 간 의견 일치도"를 의미해서 엔진의 의미와 어긋났다.

**해결 (설계)**
- 신뢰도 = 합의도(방향이 뚜렷한 지표 중 같은 방향 비중) 60% + 점수 세기 40%, 괴리 경고 시 감점.
- 가중치를 한 곳에서만 정의해 점수 합산과 신뢰도가 같은 목록을 쓰도록 구조 정리.

**결과**
- 📏 측정 필요: 적용 후 최근 N개월 데이터로 confidence 분포가 20~80 사이에 퍼지는지 확인하고 임계값 조정.

**배운 점**
- 수치의 이름과 계산이 같은 의미인지 먼저 확인한다. 지표를 평균 내는 것과 지표들이 합의하는 정도는 다른 값이다.

## 8. 시장 페이지 로딩 지연 — 🔍 분석 완료 (코드 반영 전)

**문제**
- 시장 동향 페이지가 열릴 때 분석 대기 시간이 길었다.

**원인**
- Thymeleaf 서버 렌더링이라 컨트롤러가 분석을 전부 끝내야 HTML을 보낼 수 있다.
- `MarketDiagnosisService`가 `@Transactional` 안에서 AI를 동기 호출해서, 매일 첫 방문자는 AI 응답까지 기다리고 그동안 DB 커넥션도 점유한다.
- 오늘 코멘트가 에러 문구로 저장돼 있으면 방문할 때마다 AI를 다시 호출한다.

**해결 (설계)**
- 스냅샷 저장과 AI 코멘트 생성을 분리한다. 코멘트는 별도 빈에서 비동기 또는 스케줄러로 생성하고, 화면은 코멘트 카드만 스켈레톤과 "분석 중" 안내를 보여 준 뒤 `/api/market/ai-comment`로 채운다.
- 화면 쪽 수정본은 완료. 서버 작업은 보류 중.

**결과**
- 📏 측정 필요: 변경 전후 첫 화면 표시 시간(TTFB, LCP).

**배운 점**
- 느린 외부 호출을 렌더링 경로에서 분리해야 한다. 서버 렌더링 페이지에서는 "일부만 먼저 보여 주기"가 어렵기 때문에, 느린 부분만 비동기로 떼어 내는 설계가 가장 적은 변경으로 효과를 낸다.
